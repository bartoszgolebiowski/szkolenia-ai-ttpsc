Skąd Wziąć Prawdziwe Logi Przed Zadaniem Pytania Copilotowi?

🐳 1. Kontenery Lokalne: Docker CLI 
docker logs --tail 100 --timestamps backend_api | grep -E "ERROR|Exception"

Pobierasz ostatnie 100 linii z kontenera. Widzisz dokładny stan aplikacji tuż przed awarią, a nie tylko suchy komunikat błędu.

☁️ 2. Chmura: CloudWatch & Datadog OBSERVABILITY 
aws logs filter-log-events --log-group-name /ecs/orders --filter-pattern "NullPointer"

Filtruj po Correlation-ID lub trace_id w Datadog. Wyciągasz dokładny ciąg zdarzeń użytkownika, który doprowadził do błędu.

💻 3. Terminal & Pipeline CI TEST RUNNER 
mvn test -Dtest=OrderServiceTest#testProcessOrder -DtrimStackTrace=false

Odpalsz pojedynczy test z pełnym stack trace'em bez obcinania ramek stosu. Znasz dokładny plik i numer linii.

⚠️ 4. Złota Zasada Czystego Kontekstu NO SPAM

Nigdy nie wklejaj 5000 linii logów! Wyodrębnij 15–20 linii wokół wyjątku (Root Cause) + dane wejściowe żądania. Więcej logów = większe ryzyko halucynacji AI.

💡 Zasada inżynierska: Im lepsze dane z terminala/Dockera podasz Copilotowi, tym mniej zgadywania i bzdurnych propozycji otrzymasz w odpowiedzi.

Rozbicie Logów

2. REPRODUKCJA

Czerwony Test

Zanim cokolwiek naprawisz, napisz test, który wywala się dokładnie tym samym błędem. Jeśli nie umiesz odtworzyć — nie wiesz, co naprawiasz.

3. PLAN & CHALLENGING

Kwestionowanie Założeń

Wymuś 3 hipotezy. Zapytaj: „Dlaczego to wywaliło dopiero dziś? Czy maskujemy brak wartości, czy naprawiamy źródło?”.

4. REGRESJA: ZERO RYZYKA

Zielony Pasek & Git

Implementujesz minimalną poprawkę. Test z Kroku 2 świeci na zielono i zostaje w repo jako tarcza przed regresją.
