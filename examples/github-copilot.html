Repeated signal

Find the cause of a failing test

Situation: A release candidate is nearly ready, but one unit test has started failing after a recent change. The stack trace points through several layers and the pull request is waiting. You need to find the smallest useful next check without guessing at a fix or pasting sensitive production logs into chat.

Back to T1

Without AI

  1. Reproduce the failure and inspect the trace.
  2. Trace the code path and form a cause hypothesis.
  3. Add a check or change, then rerun the test.

Pain: It can take several rounds to separate symptoms from the cause.

With GitHub Copilot

  1. Share the failing test, relevant code, and sanitized trace in Copilot Chat.
  2. Ask for likely causes and the smallest check that distinguishes them.
  3. Inspect the suggested code path and run the check.

Tool: Copilot Chat in the IDE; it does not see runtime behavior unless relevant output is provided.

What the trainee gains

How to provide focused debugging context, form testable hypotheses, and verify suggestions with runtime evidence.

Good result

A reproduced failure, verified root cause, and targeted test that confirms the fix.

Human check: Confirm the cause from code and test results. Share only approved, sanitized logs.

Directly mentioned

Improve the quality of generated tests

Situation: A small feature is ready for review, but its test suite covers only the happy path. A teammate previously tried AI-generated tests and found that they passed while missing important edge cases. You want useful coverage, not a larger test file that only creates confidence.

Back to T2

Without AI

  1. Read the function and infer expected behavior.
  2. List edge cases and write tests in the local style.
  3. Run tests and revise weak assertions.

Pain: It takes effort to find overlooked cases and match local conventions.

With GitHub Copilot

  1. Provide the function and representative existing tests.
  2. Ask Copilot to list missing cases before writing tests.
  3. Review each assertion, edit it, and run the relevant test suite.

Tool: Copilot Chat or inline suggestions plus the repository’s normal test runner.

What the trainee gains

How to derive tests from behavior, spot boundary cases, and judge whether an assertion proves the outcome.

Good result

Focused tests pass and meaningfully detect a regression in the behavior being tested.

Human check: Passing generated tests do not prove the test design is complete; review every assertion.

Repeated signal

Review a Copilot-assisted change

Situation: A pull request is ready, but the author used Copilot and now worries they have missed an assumption. The reviewer has limited time and needs to focus on behavior, missing tests, and risky changes rather than stylistic nits. The goal is a better review, not an AI-generated approval.

Back to T3

Without AI

  1. Compare the change with the ticket or requirements.
  2. Inspect affected code and tests.
  3. Find gaps, fix them, and rerun checks.

Pain: Review effort can be high, and unstated assumptions are easy to miss.

With GitHub Copilot

  1. Provide Copilot Chat with the ticket and relevant diff.
  2. Ask for prioritized mismatches, missing tests, and assumptions with file-level evidence.
  3. Verify each finding, reject speculation, and address confirmed gaps.

Tool: Copilot Chat with approved diff/context; this is assistance, not an approval gate.

What the trainee gains

How to request evidence-based critique, prioritize findings, and measure whether review effort improves.

Good result

A verified checklist and reviewed diff, with no unresolved high-impact findings.

Human check: Treat suggestions as leads, not approval. The developer remains responsible for the change.

Repeated signal

Scope a safe legacy-code migration

Situation: The team is replacing a deprecated package call with its own wrapper. A repository search finds many usages, and some callers pass different options. A global replacement looks tempting, but one missed variation could create a regression that only appears later.

Back to T4

Without AI

  1. Search for calls and understand their variations.
  2. Plan and perform replacements.
  3. Review the diff and run regression tests.

Pain: A broad change is risky, inconsistent, and difficult to review.

With GitHub Copilot

  1. Ask Copilot to locate representative usages in the workspace.
  2. Request a migration plan with variations and open questions.
  3. Change one bounded slice, inspect it, and test before expanding.
  4. Search for remaining old calls and review the full diff.

Tool: Copilot Chat or agent mode where enabled; keep edits bounded and reviewable.

What the trainee gains

How to stage a migration, validate coverage with repository search, and review AI-generated edits.

Good result

A migration diff with no unintended old calls and passing targeted and regression tests.

Human check: Confirm behavior in each usage; do not accept broad edits without reviewing the full diff.

Repeated signal

Investigate a slow SQL job

Situation: An Oracle job that normally completes on time occasionally exceeds its window. The team has a query, a schema summary, and an execution plan, but no reliable explanation for the timeout. You need a testable optimization idea while preserving exactly the same result.

Back to T5

Without AI

  1. Inspect the query, schema, and execution plan.
  2. Identify possible bottlenecks and propose a change.
  3. Benchmark the change and compare results.

Pain: Relating query structure to plan behavior can take repeated investigation.

With GitHub Copilot

  1. Provide a sanitized query, schema summary, and execution plan in Copilot Chat.
  2. Ask for bottleneck hypotheses, uncertainties, and a test plan.
  3. Review the suggestion and test it in a non-production environment.
  4. Compare performance and verify result equivalence.

Tool: Copilot Chat can analyze supplied context; it is not connected to the database by default.

What the trainee gains

How to provide useful technical context, evaluate optimization ideas, and balance speed with correctness.

Good result

A benchmarked query change or documented hypothesis with equivalent results and measured performance.

Human check: Use approved data in non-production; verify the plan, output equivalence, and measured performance.

Directly mentioned

Turn a UI mockup into Jira-ready tasks

Situation: A project lead hands you a screen mockup and a sentence describing the desired feature. An intern or teammate needs tasks they can start, but the mockup leaves responsive behavior, validation, and error states unclear. You want a useful first breakdown without silently turning guesses into requirements.

Back to T6

Without AI

  1. Inspect the mockup and request.
  2. Break work into UI, API, and supporting tasks.
  3. Write acceptance criteria and clarify ambiguous decisions.

Pain: Task breakdown is manual, and uncertainty can be mistaken for a requirement.

With GitHub Copilot

  1. Provide an approved mockup where image input is supported, or describe relevant UI details.
  2. Ask Copilot to draft small tasks, acceptance criteria, dependencies, and open questions.
  3. Review drafts and resolve design decisions with the responsible people.
  4. Prepare Jira drafts only through a separately approved CLI, MCP, or API integration.

Tool: GitHub Copilot helps draft; Jira access comes from a separately approved integration.

What the trainee gains

How to turn requests into testable criteria, distinguish facts from questions, and create reviewable tasks.

Good result

A human-reviewed task set with clear scope, acceptance criteria, and unresolved questions called out.

Human check: A person resolves design decisions and approves every Jira write. Copilot does not grant Jira access.

Directly mentioned

Find a rule in an unfamiliar repository

Situation: You have just joined a project and a bug report says an input is rejected, but nobody remembers which layer applies the rule. The repository has several similarly named validators and tests. You need to orient yourself before proposing a change.

Back to T7

Without AI

  1. Search for names, error messages, or tests.
  2. Follow references through the code.
  3. Confirm behavior by reading or running tests.

Pain: Unfamiliar names and call paths can hide the right entry point.

With GitHub Copilot

  1. Ask Copilot Chat to locate the rule in available workspace context.
  2. Request the likely implementation path and related tests.
  3. Open those files, trace behavior, and run a focused check.

Tool: Workspace context depends on IDE configuration and the user’s existing access.

What the trainee gains

How to ask focused repository questions and trace an explanation from implementation to tests.

Good result

A confirmed code path and relevant test that together explain the rule.

Human check: Validate the answer against source and tests; Copilot cannot grant access to repositories or connected systems.

Directly mentioned

Explain a technical change to a project lead

Situation: A project lead asks what changed in the upcoming release and whether it affects a customer workflow. Your notes contain implementation details, test results, and one known limitation. You need a short explanation for the meeting that is clear without promising more than the change delivers.

Back to T8

Without AI

  1. Gather verified change notes and release details.
  2. Translate technical terms into plain language.
  3. Check impact, limitations, and caveats.

Pain: Simplifying without losing important constraints takes effort.

With GitHub Copilot

  1. Provide verified change notes and identify the audience.
  2. Ask Copilot for a plain-language draft covering impact, limitations, and risks.
  3. Compare each claim with the source notes and revise.

Tool: Copilot Chat with only the verified information you provide or authorize.

What the trainee gains

How to adapt technical detail to an audience and clearly separate fact from implication.

Good result

A concise, accurate summary whose claims map to verified release information.

Human check: Do not imply behavior, impact, or timelines that the code and release plan do not support.

Directly mentioned

Work within client data restrictions

Situation: You are stuck on a client issue and Copilot could be useful, but the client has not approved the repository or data for that service. The deadline is real, yet copying code into an unapproved tool could violate the engagement rules. You need to know what safe assistance is possible—and where the boundary means stopping.

Back to T9

Without AI

  1. Check client rules and approved tools.
  2. Keep restricted context out of unapproved services.
  3. Continue manually or ask about an approved environment.

Pain: Missing context limits assistance, but policy remains the boundary.

With GitHub Copilot

  1. Do not provide restricted code, data, or prompts to an unapproved tool.
  2. Practice the workflow in a public or synthetic repository.
  3. Use client material only in an explicitly approved environment.
  4. Confirm approval before enabling any integration.

Tool: Copilot only where expressly approved; otherwise use synthetic/public material for practice.

What the trainee gains

How to recognize data boundaries, choose safe practice material, and verify tool approval before use.

Good result

A demonstrated workflow using synthetic/public data or an explicitly approved client environment.

Human check: Copilot cannot bypass client rules. Use synthetic/public data unless an approved client environment exists.
